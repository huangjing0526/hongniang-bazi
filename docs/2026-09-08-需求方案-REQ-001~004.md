## 1. REQ-001 · 时间与出生地通用控件

### 1.1 现状

- 出生时间只有一条 12 位数字输入框（`199608101203`），老师反馈不习惯。
- 出生地是模糊搜索下拉（`lookupCity`），选完带出经度，另有经度微调框。
- 批量粘贴命例跨省重名时，盘页上方有「city-confirm-bar」让老师改选——又是一套选地方的 UI。

### 1.2 方案：两个通用组件，三处共用

纯 ESM、零依赖、无框架（与现有 `web/app.js` 一致），放 `web/components/`。

**`DateTimePicker`**（`web/components/datetime-picker.js`）

| 项 | 设计 |
|---|---|
| 字段 | 年 / 月 / 日 / 时 / 分，五个 `<select>` 一行排开 |
| 年 | 下拉，范围 **1900–2100**（与 REQ-004 万年历表覆盖范围一致，见 §4.4；现 12 位解析放到 1801，越界盘按 §4.4 提示） |
| 日 | 随年月自动收缩（2 月 28/29、小月 30），切换年月后日期越界自动钳到月末 |
| 时 | 24 小时制，每项带时辰标注：`00 子` `01 丑` `02 丑` `03 寅` … `23 子`，老师看时辰、机器取小时，两边都不用换算 |
| 分 | 00–59 下拉（老师的盘多是整点或出生证上的分钟，下拉比敲字稳） |
| 值 | `{ year, month, day, hour, minute }`，与 `state.input` 现有字段完全一致，引擎无需改 |
| 与 12 位速记的关系 | **保留 12 位框**，两者双向同步：敲 12 位 → 五个下拉跟着变；改下拉 → 12 位框文本跟着变。老师用哪种都行 |

**`RegionPicker`**（`web/components/region-picker.js`）

| 项 | 设计 |
|---|---|
| 形态 | 省 → 市 → 区县 三级联动下拉 + 一个搜索框（打字直接跳到匹配项，复用现有 `lookupCity` 排序逻辑） |
| 数据 | 复用 `engine/data/cities.json`（3206 条，展示名已是「省 市 县」三段），加载时按空格切段建树，**不新增数据文件** |
| 特例 | 直辖市「北京市 北京市 东城区」折成两级显示（北京市 → 东城区）；省直辖县级「湖北省 仙桃市」到市级即为叶子 |
| 精度提示 | 只选到省/市时沿用现有 `city-precision-hint`（地级市坐标是辖区质心，引导选到区县） |
| 值 | `{ name, lng, lat, level: 'province'\|'city'\|'county', approx }`；经度微调框保留，手改经度仍视为 `cityKnown=true`（现有语义不变） |

组件接口统一为：

```js
const picker = mount(el, { value, onChange });   // 返回 { getValue, setValue, destroy }
```

**三处接入**：① 快速录入表单（替换 12 位框下方 + 城市搜索框）；② 盘页 `city-confirm-bar`（跨省重名改选，换成 `RegionPicker`，删掉那套独立 UI）；③ 万年历页（REQ-004）。

### 1.3 不做 / 待确认

- 不加「时辰不详」「只知道时辰不知道分钟」这类新选项——没提，且会牵动契约（`Verdict.timeSource`）。如果老师后续提，另开需求。
- **待确认 A**：12 位速记要不要保留？我建议保留（键盘党老师和批量粘贴都靠它，去掉等于改流程）。
- **待确认 B**：「分」用下拉还是数字框？我建议下拉，理由在上表。

## 2. REQ-002 · 金用黄色

### 2.1 根因

`web/index.html:25-26`：

```css
--earth: #8A6A3B;
--metal: #8A6A32;
```

两个色值肉眼不可分，所以老师看到「酉」跟「戌丑辰未」一个颜色。**不只是酉，庚辛申酉四个字都受影响**；它们共用 `.metal` 类和 `--metal` 变量，改一处全好。

### 2.2 方案

改 `--metal` 为可读的金黄。约束：底色是米纸 `#F6F1E8`，纯黄在纸色上对比度不够，实测：

| 候选 | 与纸底对比度 | 结论 |
|---|---|---|
| `#C9A227`（典型金黄） | 2.15 | 26px 大字勉强、12px 藏干读不清，否 |
| `#9A7A0A`（暗金） | 3.62 | 26px 天干地支达标（大字 ≥ 3:1），12px 藏干不达标 |

所以采用**两级**：

- `--metal: #9A7A0A` 给 26px 的天干/地支主字与 `wx-dot` 圆点；
- 12px 的藏干行里，金属性字改为 **暗金字 + 淡黄底衬**（新增 `--metal-soft: #F7EBB8`，做成小圆角底），颜色不够对比度靠底衬补，一眼能看出「这几个是金」。

同时把 `web/README.md` 里「金黄」的配色规范落实。**待确认 C**：改全部四个金字（推荐）还是只改酉？只改酉在代码里反而要单独开特例，不建议。

**改动文件**：`web/index.html`（CSS 变量 + `.zang-gan .metal` 一条规则），`web/app.js` 不动。

## 3. REQ-003 · 节气当天默认「早晚子时」并提醒

### 3.1 需求解读（需要老师/你确认的口径）

- **「24 节气当天」**：按 24 个（12 节 + 12 中气），不只 12 节。老师原话是 24，照做；现有 `JIE_QI` 风险（距交节 < 6 小时）只看 12 节，两者并存、各管各的。
- **「当天」按哪个钟**：按**标准北京时**的公历日期（年月柱交节用的就是这个钟，见 `engine/src/chart.js` 冻结口径）。真太阳时会把日期挪到前后一天，如果按真太阳时判「当天」，同一个出生记录换个出生地会一会儿是节气日一会儿不是——不稳。
- **「默认勾选」与老师全局偏好的关系**：现在子时流派是老师手动切、且记住的（`saved.sect`）。自动改成早晚子时必须不吞掉老师的选择，规则见 3.2。

### 3.2 方案

**引擎**（`engine/src/risk.js`、`engine/src/contract.js`）

- `contract.js` 新增 `RISK_KIND.JIE_QI_DAY`，级别 `INFO`。
- `risk.js` 新增 `jieQiOfDay(beijing)`：取 `lunar.getJieQiTable()` 全部 24 项，找公历日期 == 北京时日期的那一项；命中则推：
  `{ kind: JIE_QI_DAY, level: INFO, message: '今日为「白露」，交节 2026-09-07 22:41（北京时间）。已默认按早晚子时排盘；如您师承子初换日，可在工具栏切回。', affects: ['day','time'], meta: { name, at } }`
- 节气时刻来源先用 `lunar-javascript`；REQ-004 的冻结表落地后**换成表**，对上层透明（§4.3）。

**前端**（`web/app.js`）

- `state.input.sect` 语义拆成两层：`sectPreference`（老师手动选的、持久化的，现有行为）和每盘的 `sectOverride`。
- 排盘后若 `risks` 含 `JIE_QI_DAY` 且本盘老师**没有**手动动过子时开关 → 本盘生效值取 2（早晚子时），工具栏单选跟着变；
- 老师在本盘手动切回 1 → 记 `sectOverride=1`，本盘不再自动改；
- 切到下一盘 / 换命例 → `sectOverride` 清空，回到老师偏好，再按规则判一次；
- 提醒展示在第一屏风险条（现有 `risk-banner-box`），INFO 样式；
- 裁定回传的 `options.sect` 记**实际生效值**（现有逻辑已是如此，无需改），所以后台能看出哪些盘是自动切的：`options.sect=2` 且 risks 含 `JIE_QI_DAY`。

**批量模式**：每条命例载入时同样走这一套。

**回归用例**：白露当日 23:30（北京时）兰州 → 默认 sect=2，且 ZI_SHI + JIE_QI_DAY 同时亮；立春当日 → JIE_QI_DAY 与 JIE_QI（<6h）可同时出现，文案不重复。

### 3.3 待确认

- **待确认 D**：以上「当天按北京时」「24 项都算」「手动切回后不再自动改」三条口径。

## 4. REQ-004 · 自动对照万年历（重点）

### 4.1 需求解读

老师核盘的习惯：翻纸质万年历，找到出生那天那一行，核**日干支**，再看本月**节的交节时刻**核月柱/年柱，再按日干推时柱。「自动对照」= 工具把这一页替老师翻出来并**自动比**；「准确度要求很高」= 节气时刻精确到分钟、日干支纪日不断链、闰月不错——因为老师会拿书来对，差一分钟落在交节两侧就是整柱不同。

现状的短板：历法只有 `lunar-javascript` 一个来源（寿星系），没有独立校验；§11 已经承认 tyme4ts / sxtwl 与它同源，「三源对账」降级成了差分回归，但**差分回归至今没做**。

### 4.2 万年历页（老师看的）

新增 Tab「万年历」，同时盘页加一个入口「对照万年历」——带着当前盘的日期、时间、出生地跳过去，页面顶部就是 REQ-001 的 `DateTimePicker` + `RegionPicker`（老师也可以不从盘进来，直接查任意一天）。

页面内容仿一页纸质万年历，从上到下：

| 区块 | 内容 | 用来核什么 |
|---|---|---|
| **月页** | 选中月份逐日一行：公历日 · 农历（含闰月）· 日干支 · 节气标注（含交节时刻）· 星期。出生日整行朱砂高亮 | 日柱（老师核的第一件事） |
| **本月节气** | 本月的节与气各一条：名称、交节时刻（北京时间，精确到分）、距出生时刻多少小时分钟；出生时刻落在节前/节后用箭头标出 | 月柱、年柱（立春） |
| **本日时辰表** | 12 行：时辰 · 北京时区间 · **本地真太阳时对应的北京时区间**（由 `RegionPicker` 经度算出，如「兰州 子时 = 北京时 00:05–02:05」）· 该时辰的时柱干支；早子/晚子两派并列各给一列 | 时柱、子时分歧 |
| **对照结论** | 从盘页进来时显示：本盘四柱 vs 万年历页推得的四柱，逐柱「一致 / 差异」。差异只标位置、不给结论（沿用现有红线） | 「自动对照」本身 |
| **来源与精度声明** | 「节气时刻据本工具冻结表（北京时间）；1900–1950 年各版万年历因 ΔT 模型差异可相差 1–2 分钟」 + GeoNames 署名 | 老师拿不同版本的书来对时有心理预期 |

**与 REQ-003 的关系**：万年历页天然显示「今日是节气日」，风险条的文案里加「查看万年历 →」链到这里。

### 4.3 准确度底座（机器保证的）

原则：**不再只信一个来源**。分三件事。

**① 节气冻结表** `engine/data/jieqi-1900-2100.json`

- 24 × 201 年 = 4824 条，北京时间（UTC+8）精确到分。存法：每年一个数组 24 个「距 1900-01-01 00:00 的分钟数」整数，~60 KB，随 dist 发布（`scripts/build.mjs` 白名单加一行）。
- **生成方式**：自己写一份独立实现 `engine/astro/jieqi.mjs`——Meeus《Astronomical Algorithms》第 25/27 章太阳视黄经 + VSOP87 截断项 + ΔT（Espenak-Meeus 多项式），求太阳黄经 = 15°k 的时刻。这与寿星系是**不同代码、不同作者**的实现，才算独立。它**只在构建/测试时跑**，不进浏览器。
- **验证三关**（进 CI，`engine/test/calendar.test.js`）：
  1. 对 `lunar-javascript`：4824 条逐条差分，允差 ±1 分钟；超出的条目列出来人工裁；
  2. 对**香港天文台**《公历农历对照表 1901–2100》：节气**日期**全部一致（HKO 只给到日，不给分钟，但它是官方独立来源）；
  3. 对**紫金山天文台**每年公布的节气时刻（近年的《中国天文年历》摘要，可拿到的年份逐条抄进 `engine/data/jieqi-anchors.json` 作锚点）：分钟级一致。
  三关有一关不过的条目，表里加 `overrides: [{ year, term, minutes, source }]` 人工定值并注明出处，不允许悄悄取平均。

**② 日干支纪日校验**

- 日干支本质是儒略日 mod 60，与天文无关，锚点 `2000-01-01 = 戊午`。CI 里 1900–2100 逐日比 `lunar-javascript` 的日干支与 JDN 推算，必须 0 差异——这是「纪日断链」的保险。

**③ 农历与闰月校验**

- `lunar-javascript` 的农历年月日、闰月，对 HKO 对照表 1901–2100 逐日比，必须 0 差异。HKO 表是**政府发布、独立于寿星**的来源。

**运行时（浏览器里）**

- 新增 `engine/src/calendar.js`：对外提供 `jieQiAt(year)`、`jieQiOfDay()`、`nearestJie()`，**读冻结表**；`risk.js` 与 REQ-003 改为调用它，不再直接 `getJieQiTable()`。
- 每次排盘顺手做一次差分：表 vs `lunar-javascript` 当年节气，若任一条相差 > 1 分钟 → 推 `RISK_KIND.CALENDAR_MISMATCH`（WARN）：「本年节气时刻两套历法不一致，请以万年历页为准并反馈」。正常情况永远不触发，它存在的意义是**出了问题不会静默**。

### 4.4 年份范围

冻结表覆盖 **1900–2100**。现 12 位解析放到 1801——1900 以前 ΔT 不确定性大、HKO 表也不覆盖，「准确度很高」保证不了。方案：控件限 1900–2100；12 位输入 1900 以前的盘仍可排，但风险条给 WARN「1900 年前节气时刻未经验证」。**待确认 E**。

### 4.5 待确认

- **待确认 F**：万年历做成独立 Tab（推荐，老师可以脱离命例查）还是盘页里的抽屉？
- **待确认 G**：HKO 与紫金山的数据抓取一次入库缓存（`engine/data/.cache/`，同 cities 的做法）；紫金山锚点年份先做 2020–2026 这几年，够不够？
