## 1. 项目是什么、为什么做

### 1.1 起因

红娘机构用市面上的「问真八字」App 排盘，反馈「98% 是对的，只有部分场景有错误」。我们做一个可测试、可归因的排盘工具，先让老师试用、采集出错的真实命例，再做成正式产品。完整调研见 `docs/2026-09-03-红娘八字排盘-调研与MVP方案.md`，三方对抗审查与裁决见 `docs/reviews/2026-09-03-*.md`。

关键定位（2026-09-03 裁决后定下，至今有效）：

- **不打「更准」，打「可归因」**。任何与其他工具的分歧，要能 30 秒定位到是历法层、口径层、神煞表还是输入错误。
- **分歧时不给「正确答案」**，只指出分歧点与两种排法。哪派对是老师的判断。
- 神煞表是冻结表，与其他工具条目不同属「表不同」，不是漏算。
- 不做 AI 批命、不做合婚百分制、不用 GPL 许可的排盘实现。

### 1.2 两个阶段

| 阶段 | 面向 | 状态 | 代码位置 |
|---|---|---|---|
| **试用版**（B 档 MVP） | 老师，无账号，命例存浏览器本地并同步到服务器 | 线上运行中；2026-09-11 决策 D-0 后**冻结**，只修 bug，一期上线后一个月退役 | `web/`、`cloud/`、`deploy/`、`data/` |
| **一期正式版** | 需要记录和查看命盘的用户；账号、命例、基本排盘、命盘详解、研判记录 | PRD v1.11 已批准；Antigravity 原型二轮进行中；前后端未开工 | `app/`（前端）、`server/`（服务）目前只有 README |

两个阶段**共用 `engine/`**（历法与命理引擎）。这是唯一的命理逻辑来源，前端不写任何命理逻辑。

## 4. 引擎：你必须知道的口径

引擎的分层（`engine/README.md`）：

```
钟表时（出生记录原样）
  ─[夏令时回拨]→  标准北京时  ──→ 年柱、月柱（按北京时交节）、起运
  ─[+经度差 +均时差]→ 真太阳时  ──→ 日柱、时柱
```

冻结口径（已登记为业务规则 BR-006～BR-011，改动要走版本审核）：

- 年柱以立春、月柱以十二节交节时刻换，按北京时判定。
- 1986–1991 夏令时必须回拨。**1988 年起日是 04-17 不是 04-10**，网上普遍抄错，测试锁住了。
- 真太阳时只改日柱与时柱。
- 子时换日默认「子初换日」（sect=1），可切「早晚子时」（sect=2）。节气当天试用版自动默认早晚子时（REQ-003）。
- 夏令时结束日 01:00–01:59 同一钟表时对应两个瞬间，引擎目前输出**双盘**。一期决策 D-9 改为「录入时追问，答不上按调回前算并标注另一种」，**引擎尚未改**。
- 时辰未知：一期要求时柱及派生字段一律 `*`，大运整体换成「时辰未知，无法起运」。**引擎契约尚未允许 `luck` 为空**。

数据底座：

- 节气冻结表 `engine/data/jieqi-1900-2100.js`，由独立天文算法生成，过三关验证（与寿星系差分、香港天文台日期、香港天文台分钟级）。**勿手改**，改走 `scripts/build-jieqi.mjs`，验证方法在 `engine/data/jieqi.SOURCE.md`。
- 城市名录：民政部 2023 年区划表 + GeoNames 坐标（**CC BY 4.0，界面必须署名**，一期放「关于」页）+ Wikidata 补 51 条。见 `engine/data/cities.SOURCE.md`。
- 历法库 `lunar-javascript`（MIT）只做底座；十神、藏干、十二长生、神煞、关系表全部自研，因为年月柱与日时柱可能来自两个不同时刻。

契约：`engine/src/contract.js` 是引擎对外唯一形状（`Chart`、`Relation`、`Flow`、`Luck` 等 typedef），前端只消费它。改契约先改这个文件，再通知其他方。

已知待核的两处表数据（验收时顺带发现，见决策表第七节）：

- 六破表 `branch-relations.js` 第 93 行用卯未、午戌，通行是卯午、戌未。要对老师文档 K12 原文核。
- 三刑命名与《三命通会》相反（寅巳申记恃势、丑戌未记无恩），按老师文档 K10。界面暂只写「相刑」。

## 9. 协作方式与文档流转

本项目由多个 AI 分工干活，人只做决策和验收。总规则在 `~/workspace/os/AI协作路由.md`，本项目的实际分工：

| 角色 | 干什么 | 边界 |
|---|---|---|
| Claude | 总调度：写 PRD 与决策表、写任务书、验收回执、改引擎与文档、维护决策表 | 决策表只由 Claude 维护、只由产品裁定 |
| Codex | 引擎与后端实现（万年历页、裁定表单三修都是它做的） | 不碰 `web/` 样式与 `prototype/` |
| Antigravity | 视觉体系与原型、前端样式 | 不碰 `engine/`、`cloud/`；不 git add / commit |
| Grok | 外部事实调研 | 不写代码 |

流转形式固定：`docs/日期-任务书-谁-什么.md` → `docs/reviews/日期-回执-谁-什么.md` → `docs/reviews/日期-验收-谁-什么.md`。任务书必须写硬约束（只写哪些文件、不 commit）；回执必须**只写实测到的**，一轮回执曾有三条与实物不符，这是验收时要盯的点。

三方并行的防撞规则：只写自己那列目录；接口以 `contract.js` 为准，改形状先回来说；不 git add / commit，由集成人统一提交。

产品纠正做法时要登记到 `~/workspace/os/纠错登记.md`，同一错误第二次出现必须提议入规。
