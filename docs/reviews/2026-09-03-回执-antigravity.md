## 致命项

### A-1：L2（输入错）与 L5（老师私家表）在产品逻辑上无法自动判定，「30 秒定位到层」是假承诺

- **攻击面**：2. 「可归因」定位能不能落到 UI
- **判定**：致命
- **证据（文件与行）**：
  - `docs/2026-09-03-红娘八字排盘-调研与MVP方案.md:305`：
    > `| L2 | 输入数据 | 时间来源不可靠、出生地留了默认值、公历农历混、闰月 | 有，但错不在引擎 |`
  - `docs/2026-09-03-红娘八字排盘-调研与MVP方案.md:308`：
    > `| L5 | 老师记忆或私家表 | 与任何公开表都对不上 | 无 |`
  - `docs/2026-09-03-红娘八字排盘-调研与MVP方案.md:320`：
    > `产品职能改写为：任何一次分歧，30 秒内定位到哪一层，并给出可切换的开关。`
  - `prototype/index.html:464-482, 608-643`：
    现有的口径抽屉仅有真太阳时与子时开关，对照抽屉仅有两行静态干支比对，完全没有分层诊断逻辑，更无输入来源审计和私家表对照功能。
- **推翻文档**：
  - 推翻 §11.1 核心职能定义：
    > `产品职能改写为：任何一次分歧，30 秒内定位到哪一层，并给出可切换的开关。`
  - 连带推翻 §2 结论表：
    > `定位｜不打「更准」，打「可归因」；任何分歧 30 秒定位到层（第 11 节）`
- **详细论证**：
  1. **L2 无法被算法闭环定位**：排盘系统只接收表单输入的值（例如“1990-05-05 12:00 兰州”）。如果相亲客户口述的是农历而红娘误选了公历、客户家属把“午时”误记为“12:00整”，或是红娘未修改默认地点“北京”，软件从纯数据层面看完全合法。系统根本不可能在不调取公安户籍原始档案或询问口述者本人的情况下，自动判定“这是 L2 输入错误”。系统至多能弹出“该日有闰五月，请复核”或“当前为整点，距时辰边界近”的启发式弱提示，绝无可能“30 秒自动断定为 L2”。
  2. **L5 无法被算法识别与定位**：当红娘报出一个既不符合我方算法（L1/L3）、也不符合问真、更不符合公开古籍表（L4）的四柱时，系统在逻辑上只能得出“该盘与已知库全部不符”的结论。此时系统无法区分究竟是：① 老师记忆笔误（L5），② 老师漏看输入（L2），③ 我方引擎存在未知边界 Bug，还是 ④ 老师掌握某支未公开的家传口诀。若系统在界面上提示“属于 L5 老师私家表/记忆偏差”，属于无根据的指控，直接违反 §11.3“分歧时不判老师错”的红线；若不提示，则根本做不到“定位到 L5”。
  3. **五层定位兑现度不足 60%**：5 层归因中，软件真正能靠代码精确对比的只有 L1（天文历法是否漏算夏令时/经度/均时差）、L3（是否因流派开关导致子时/节气基准差异）以及 L4（是否因预设神煞字典版本差异）。对占据实际投诉大头的 L2 与 L5，软件不仅无法自动判定，更不可能“给出可切换的开关”（系统怎么给一个“切换到老师脑中私家表”的开关？）。
- **建议怎么改**：
  推翻“任何分歧 30 秒定位到层并给出开关”的绝对化宣传，重写 §11.1：
  > “产品职能改写为：针对已建模的历法规则（L1）、流派开关（L3）与神煞字典（L4），30 秒内定位差异源头并提供实时切换；针对输入疑点（L2）提供边界与闰月预警，针对无法识别的差异（L5）保留自定义备忘标注，不承诺全自动归因。”

### A-2：核心护城河「合婚与客户档案」与 MVP 交付范围生死脱节

- **攻击面**：5. §11.1 三件护城河，哪几件是真的
- **判定**：致命
- **证据（文件与行）**：
  - `docs/2026-09-03-红娘八字排盘-调研与MVP方案.md:322-327`：
    > `排盘是入场券。可防守的是问真作为通用个人工具做不到的三件：1. 老师/机构的口径与神煞表固化成配置 2. 机构级一致性…… 3. 合婚与客户档案`
  - `docs/2026-09-03-红娘八字排盘-调研与MVP方案.md:178`：
    > `| 合盘 / 大运流年 | 二期 | 细盘灰显占位，不造假大运 |`
  - `docs/2026-09-03-红娘八字排盘-调研与MVP方案.md:191-192`：
    > `| B 试用 MVP | A + 问真基本排盘字段 + 交界预警 + 老师备注 | 8–12 日 | 当前 |`
    > `| C 合盘 | B + 日柱合冲、十神互看、合婚神煞 | +4–5 日 | 老师认四柱后再做 |`
  - `docs/2026-09-03-红娘八字排盘-调研与MVP方案.md:194-202`：
    §7.2 页面清单全部围绕单人基本排盘展开，大运流年为二期占位，无任何合婚分析及档案库页面。
  - `prototype/index.html:587-592`：
    原型 Tab 3（专业细盘）仅有一个写着“二期 · 起运与流年”的空白占位卡片，没有任何双人合盘或客户档案列表。
- **推翻文档**：
  - 推翻 §11.1 中将 `3. 合婚与客户档案` 列为当前产品防守护城河的结论。
  - 连带推翻 §2 结论表：
    > `MVP 档位｜B：对齐问真「基本排盘」+ 口径/对照/朱批`
- **详细论证**：
  1. **战略防御假设与战术交付范围脱节**：§11.1 极为清醒地指出：“单人排盘是不可赢的战争”、“问真免费且老师已有肌肉记忆，在精度上打免费工具是错误战场”、“可防守的是合婚与客户档案”。这一战略判断完全正确，但接下来的执行方案却立即背叛了这一前提——§6、§7.1、§7.2 白纸黑字将“合婚合盘”明确剔除出当前范围，划归“二期 / C 档”。
  2. **B 档 MVP 处于零防御裸奔状态**：当前 1 全栈投入 10~12 天全力打造的 B 档产品，实际交付物本质上是一个“去掉了大运流年、仅带 20 个硬编码神煞、加了真太阳时开关与简陋对照抽屉的问真单盘克隆版”。它恰恰落入文档自身警告的“在问真的绝对优势战场与问真拼单人排盘”。老师打开 B 档产品，看不到合婚，看不到客户库，只会立刻拿它和问真比神煞数量、比界面熟练度，而这两点问真完胜。
  3. **逻辑死锁**：“老师认四柱后再做合婚（§7.1）”是一个产品死锁逻辑。老师用着免费且功能更全的问真，根本没有动力在单盘阶段“认”一个功能残缺的 Web 原型；唯有直击其痛点的“男女双盘合婚与相亲档案管理”，才是吸引老师放弃问真、参与测试的真正诱因。
- **建议怎么改**：
  重排档位与工期优先级，二选一：
  - **方案 A（保护城河）**：推翻 §7.1，将 C 档拆解，砍掉单人细盘中繁复的十神副星与长生细节，将“男女双人日柱合冲、年命纳音合、相亲客户档案卡片”直接并入 MVP，确保第一版交付物就具备问真不具备的“红娘合婚工具”形态；
  - **方案 B（保工期）**：若坚守 10~12 天只做单盘排盘，则必须在 §11.1 中实事求是删去“合婚与客户档案是护城河”的话术，向决策层明示：“B 档 MVP 仅为历法算法可行性验证桩，本身不具备任何商业防守壁垒与客户黏性”。

  - `prototype/index.html:627-643`：

- **推翻文档**：
  - 推翻 §7.2 页面清单的完备性（遗漏了关键业务承载容器“归因面板”）。
  - 推翻 §9 实现路径工期评估的前提（未包含可配置神煞字典与归因面板的开发量）。
- **详细论证**：
  §11 提出了极具设想力的分诊机制（“不争论，进归因面板”），但回顾已冻结的产品设计，根本没有给“归因面板”留出位置。现有的“对照抽屉”极其简陋，只能高亮四柱不同，无法展示分歧属于哪一层、为何不同、流派依据是什么。同时，§11.1 声称“神煞表固化成配置”，而 §6 和 §7.3 却采取完全相反的工程做法——写死 20 个神煞硬编码在代码里，其余“缺了不编”。一个硬编码神煞表的系统，如何能兑现“给老师/机构固化私家神煞表配置”的护城河？新加的 §11 漂浮在旧架构之上，未向下穿透修正页面清单与数据模型。
- **建议怎么改**：
  1. 在 §7.2 补全“归因面板”规格：明确它是对照抽屉展开态，还是在排盘页中作为内嵌诊断卡片呈现；
  2. 澄清神煞配置范围：明确 B 档神煞表是否支持增删改查。若不支持，必须在 §11.1 改为“二期实现神煞配置化，B 档仅支持内置冻结表的来源备注查看”。

### A-4：§13.1「分歧风险扫描」作为“首个价值证明”会触发红娘防御心理，引发信任灾难

- **攻击面**：4. §13.1 分歧风险扫描的呈现风险
- **判定**：重大
- **证据（文件与行）**：
  - `docs/2026-09-03-红娘八字排盘-调研与MVP方案.md:408-417`：
    > `只需要出生日期时间 + 出生地经度，不需要排盘引擎。批量扫老师现有客户库或最近 20 个盘，标出四类风险，只标风险不给结论……这张表本身就是给老师的第一个价值证明，成本远低于把引擎做完。`
  - `docs/2026-09-03-红娘八字排盘-调研与MVP方案.md:412-415`：
    表内直白写出影响：`时柱可能整柱错`、`日柱两派不同，连累全部十神`、`月柱或年柱分歧`。
  - `docs/2026-09-03-红娘八字排盘-调研与MVP方案.md:343`：
    > `§11.3 三条红线第 2 条：分歧时不判老师错。`
- **推翻文档**：
  - 推翻 §13.1 核心断言：
    > `这张表本身就是给老师的第一个价值证明，成本远低于把引擎做完。`
- **详细论证**：
  1. **严重的行业人情世故误判**：红娘老师不是等着 CI 报 Lint Error 的软件工程师。在相亲机构中，老师过去经手的客户均已收取服务费，有些甚至已经结婚或正在相亲交往。若一个外部技术团队拿着脚本扫描其 20 个客户，然后递上一份报告赫然写着“有 6 个客户命中风险：时柱整柱错、十神全变、月柱分歧”，老师的第一反应绝非“这个新工具好专业、好有价值”，而是极度的惊恐与抗拒：“你在质疑我的业务能力？万一客户知道了找我退费砸招牌谁负责？你们这套自研算法到底靠不靠谱就跑来挑我的刺？”
  2. **违反红线精神**：虽然文档口头强调“只标风险不给结论”，但当着老师的面给其客户打上“时柱整柱错”的红色标签，本身就是在实质性宣告“你以前用的工具有大错，你以前出的盘有问题”，这赤裸裸践踏了 §11.3“分歧时不判老师错”的红线。
  3. **阻断后续先行动作**：一旦第一步让老师产生了被冒犯和被挑衅的感受，老师绝不可能配合开展 §13.2 的“错例采集表”，先行动作链条将在第一天彻底断裂。
- **建议怎么改**：
  1. 禁止主动拿老师的历史客户库做“批量排错扫描”；
  2. 将 §13.1 的定位从“给老师的第一个价值证明”修改为“内部回归集冷启动校验”，扫描脚本仅用于技术团队对公网公开命例或团队自有测试数据的风险摸底；
  3. 若向老师展示，必须包装成“疑难边界辅助核验单”，话术调整为：“协助老师识别出生证夏令时及交界模糊时段，方便老师向相亲客户进一步核对出生细节，展现专业严谨度”。

### A-5：「机构级一致性」是对红娘行业的伪需求臆想，且与玄学师承冲突

- **攻击面**：5. §11.1 三件护城河，哪几件是真的
- **判定**：重大
- **证据（文件与行）**：
  - `docs/2026-09-03-红娘八字排盘-调研与MVP方案.md:325`：
    > `2. 机构级一致性——同一机构多位老师出的盘口径统一，卷宗可交付客户`
- **推翻文档**：
  - 推翻 §11.1 中将 `机构级一致性` 列为可防守护城河的断言。
- **详细论证**：
  1. **违背玄学门派师承客观规律**：民间命理学不存在国家统编教材。在婚介所或相亲机构中，合作的命理老师通常各承师门（有的专研子平真诠，有的宗盲派，有的严守早晚子时，有的坚持子初换日）。对专业玄学从业者而言，命理口径代表其门派尊严与“断盘手感”，强行用软件剥夺其口径自由度、要求全机构“大一统”，是对老师专业自尊的冒犯，极易引起资深老师的抵制和跳槽。
  2. **机构真实痛点是外显形象，而非底层口径**：红娘机构管理者真正关心的“一致性”，是**对外部客户呈现的卷宗视觉一致性与品牌正规感**（例如统一采用高级的朱砂卷宗 UI、统一印制机构 Logo、统一避免问真 App 的杂乱广告与黑金山寨感），而非强行在机构内部推行“算法思想大一统”。将后台口径强行抹平当成核心卖点，是程序员将企业级架构的一致性幻觉强加给松散合作制的手艺人群体。
- **建议怎么改**：
  重写 §11.1 护城河第 2 条：

## 崩溃推演结论（攻击面 6）

> **推演前提**：假设 Grok 核查证实「问真八字」App 实际上已支持夏令时自动回拨与真太阳时修正（例如在设置中具有历法校正开关，或 VIP 排盘中已默认处理 1986–1991 历史夏令时）。

### 1. 连锁崩塌效应

若该假设成立，整个方案的新增战略根基将遭遇**毁灭性打击**：

1. **§12.1「唯一硬赢点」瞬间清零**：
   文档将夏令时断言为“唯一能硬赢的点，1986–1991 年出生者 20.6% 时柱整柱错，作为给老师的第一个 Demo”。一旦问真支持该特性，我方拿着夏令时案例去老师面前演示，老师只需打开问真对应开关，即可当场排出一模一样的四柱，我方设立的核心赢点当场沦为笑话。
2. **§11.2「三源对账」裁决体系失去着力点**：
   三源对账的判定矩阵中，唯有一条能硬性判问真错（即“三源一致 vs 问真不同 → L1 问真错”）。若问真天文历法层毫无漏洞，该分支将永远无法触发。
3. **§11.1「可归因」退守防线沦为空谈**：
   文档在 §11.1 已承认在 L3（口径）、L4（神煞）、L5（私家表）上没有客观裁判，无法在排盘精度上击败问真；而本回执 A-1 又证实了 L2 与 L5 无法被软件自动定位。如果连唯一的 L1 硬胜算都不复存在，排盘层面的分歧将彻底退化为无休止的门派主观争吵。
4. **商业生存空间彻底关闭**：
   面对问真八字免费、熟练度高、神煞库超 100 个、自带大运流年及社区生态的成熟壁垒，一个耗时 10~12 天研发、神煞仅 20 个、无大运流年、无移动 App 的简陋 Web 排盘工具（B 档 MVP），在技术内核毫无差异化优势的前提下，将遭遇彻底的商业自杀。

### 2. 最小可行退路决策

基于上述推演，项目组面临两种决断：

* **退路 A（业务模式极速调头：从「排盘引擎」转向「红娘婚书交付与合婚 CRM」）**：
  * **行动原则**：立刻彻底停止在排盘算法、三源对账、历法自研上的资源投入。不与问真在四柱生成上竞争。
  * **产品重构**：
    1. 允许红娘继续使用问真排盘，甚至在前端提供“问真截图 OCR / 问真干支一键粘贴导入”功能；
    2. 将原定二期的合婚功能（C 档）全面提前，专注开发问真不具备的垂直功能：**双人八字日柱合冲图谱、纳音相生矩阵、相亲男女五行互补雷达图**；
    3. 把核心开发精力押在 UI 朱砂卷宗的**极佳视觉交付物（支持一键导出带红娘机构 Logo、可打印装裱的精美相亲婚书与合婚报告）**。
  * **商业卖点**：“问真负责算盘，我们负责帮你把盘包装成客单价 3000 元的精美相亲卷宗，并管理你的相亲客户库”。

* **退路 B（立即终止项目，止损全栈工期）**：
  * **行动原则**：若团队或资方核心诉求是“做一套自研底层排盘引擎”，且无意涉足红娘深度业务服务与交付物设计，则**不存在任何可行的局部调整方案，应在接引擎代码写下第一行前，立即全案终止**，避免浪费 10~12 天的人力成本。
