## 三、关键取舍说明

### 1. media query 为什么明确保留 px 而不换成 rem
本轮重构明确将 media query 中的视口断点（如 `1024px`、`760px`）保留为 `px`，核心考量如下：
- **场景目标是解决「字号放大」与「双栏核盘」并存的痛点**：老师在 iPad Pro（视口宽 1024px）核盘时，首要需求是「在字号调大后依然能左右双栏对照」。
- **如果断点换算为 rem 会发生严重倒退**：若断点声明为 `64rem`（1024 ÷ 16），当用户在系统或浏览器中将字号设为 150%（根字号 24px）时，1024px 的物理视口换算为 rem 仅等价于 `42.66rem`（1024 ÷ 24），会立即跌出双栏断点区间，导致页面被强行顶回单栏，裁定表单再次掉到 y=1122 的屏幕下方，使得「放大」与「双栏」相互排斥。
- **保留 px 断点的解耦价值**：将视口几何尺寸与内容文字比例解耦，保证在 1024px 及以上设备上，无论文字放大到何种程度，双栏对照布局始终坚固不塌（实测在 150% 字号下 `1024×768` 视口无横向溢出且双栏完整渲染）。

### 2. 矮屏特例 `@media (min-width: 1024px) and (max-height: 640px)` 的处理 rationale
- 原规则的作用是：在双栏生效的宽屏上，如果垂直高度受限（≤ 640px），取消右栏裁定框 `.verdict-box` 的 `position: sticky` 吸顶和内部局部滚动，让其自然在右栏垂直流动，防止 sticky 容器内部可用高度被压缩到极短而难以操作。
- 既然本轮已将双栏的起始断点由 1080px 下移到 1024px，则 1024px~1079px 区间已处于双栏布局之下。若矮屏特例仍滞留在 1080px，会导致 1024px 矮屏出现双栏强行 sticky、内滚区过短的体验劣化。因此将该特例触发门槛同步降至 1024px，保持行为逻辑自洽。实测 1024×640 视口下，右栏自然 static 排布，页面横向溢出严格为 0。

## 六、审查中发现的新问题（写进回执，未动手改）

在重构与测试过程中观察到以下几处细节，属于既有逻辑或未来潜在优化点，本轮严格遵循不扩大事态原则，未做改动：
1. **`prototype/index.html` 产生断代分叉**：原型文件仍保留 1080px 断点与全量 px 字号。后续若原型需要作为新的对齐基准，建议单排一轮原型同步任务。
2. **`--sticky-top: 128px` 仍为硬编码 px**：虽然其在 1024px 和 1440px 下工作正常，但当字号放大到 150% 时，顶部毛玻璃导航头实际高度由约 117px 膨胀到约 148px，导致 sticky 吸顶的裁定框轻微被顶部遮挡约 20px。当前通过右栏容器内边距和滚动余量未产生致命问题，后续可考虑使用动态计算或将 `--sticky-top` 改为根据 header 内容自适应。
3. **移动端卡片内边距在极限字号下偏紧**：在 375px 宽视口下如果开启 150% 字号，命主卡片与排盘表格的固定 padding（如 12px~14px）会导致每行文字换行增多，排盘十行表格虽无横向滚动，但视觉密度显著增高。后续可评估是否需要为超小屏幕搭配阶梯内边距。
