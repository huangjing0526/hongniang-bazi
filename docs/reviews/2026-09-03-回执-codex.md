## 致命项

### C-1：20.6% 被写成了人群事实

- 攻击面：2
- 判定：致命
- 证据：

定义：

- \(S=P(\text{出生日期落在夏令时生效区间})\)
- \(A=P(\text{出生钟表时落在某时辰边界后 60 分钟}\mid\text{夏令时期间})\)
- 忽略夏令时造成时柱翻转的比例为 \(R=S\times A\)

文档实际代入的是：

```text
S = 903 / 2191 = 0.4121406
A = 12 个受影响小时 / 24 小时 = 0.5
R = 0.4121406 × 0.5 = 0.2060703 = 20.607%
```

其中 \(A=0.5\) 只在出生钟表时相对于 12 个时辰边界均匀时成立；\(S=903/2191\) 还隐含六年内每天出生概率相同。

在没有出生时刻分布数据时：

- 固定文档的 \(S=41.214\%\)，只放开日内分布，严格可识别区间是：

```text
A ∈ [0, 1]
R ∈ [0, 41.214%]
```

即 20.6% 的模型不确定度至少是 `−20.6 / +20.6 个百分点`。

- 如果连出生季节分布也不假设均匀，则纯数学界只能写 `0%–100%`；这个界太宽，不能作为业务点估计使用。

夏令时回拨是把钟表时间减 60 分钟，所以受影响区间确实是：

```text
23:00–24:00
01:00–02:00
03:00–04:00
...
09:00–10:00
...
21:00–22:00
```

因此，如果“09:00–10:00 是这批人口的显著出生高峰”成立，同时没有其他时段变化抵消，它会使 \(A>50\%\)，从而把 20.6% 推高，不会拉低。但我没有找到能代表“中国大陆 1986–1991 年全部出生、按小时且区分分娩方式”的数据，不能把这个方向性条件写成实测结果。现有可查研究只能支持计划性剖宫产明显受工作时间影响这一一般现象，不能校准本项目所需的人群参数。

- 推翻文档：

推翻 §12.1：

> “忽略夏令时的工具，这批人 20.6% 的时柱整柱错”

以及：

> “老师手上每五个这个年龄段的客户，约有一个的时柱……是错的”

并连带推翻 §2：

> “硬赢点｜夏令时：1986–1991 出生者约 20.6% 时柱整柱错”

`20.6%` 可以保留为“全天及全年均匀模型下的基准值”，不能写成老师客户群的发生率。

- 建议怎么改：

改成：

> “在出生日期跨六年均匀、出生时刻全天均匀的基准模型下，翻转率为 20.6%；真实比例取决于出生季节和分娩时刻分布。固定日期均匀假设时，缺乏历史小时数据所允许的模型区间为 0%–41.2%。”

第一个 demo 可以继续用具体错例证明能力，但不能再用“每五人一个”作为量化销售结论。

### C-2：三源对账不能支持 §11.2 的判定表

- 攻击面：5
- 判定：致命
- 证据（代码及依赖事实）：

1. `lunar-javascript` 的 EightChar 默认 `sect=2`，并提供 `setSect(1)`；同系列源代码明确写有：

```java
protected int sect = 2;
// 2晚子时日柱按当天，1晚子时日柱按明天
```

见 [6tail EightChar 源代码](https://github.com/6tail/lunar-java/blob/master/src/main/java/com/nlf/calendar/EightChar.java)。

文档自己又声明 `tyme4ts` 默认偏 `sect=1`。因此在 23:00–23:59 输入上，未经策略归一化的“三源一致”本来就不应成立。

2. `sxtwl` 的官方 Python 接口说明 `getHourGZ(hour)` 按早晚子时处理，并能给节气儒略日；它不是与 JS EightChar 完全同构的策略接口。对比前必须自行规定：

```text
输入时区
夏令时是否先回拨
真太阳时是否先修正
23:00 是否换日
交节使用北京时间还是修正时间
比较到天文原语、四柱，还是完整细盘字段
```

见 [sxtwl Python 官方说明](https://github.com/yuangu/sxtwl_cpp/blob/master/python/README.md)。

3. 三者不是三个完全独立的裁判：

- `tyme4ts` 与 `lunar-javascript` 同属 6tail 系列；
- 文档称 Tyme 的节气引自寿星；
- `sxtwl_cpp` 自述参考寿星天文历。

因此“三源一致”可能只是共同上游、共同规则或同一配置得到一致结果，不能单凭数量证明唯一正确。

4. 判定表存在逻辑越级：

```text
三源一致 + vs 问真不同
```

只能先证明“标准化输入和政策后，三个被选实现与问真输出不同”。它不能自动推出“L1，问真错”，因为差异仍可能来自 L3 配置、输入标准化错误或三个实现共享的上游缺陷。

同理：

```text
三源不一致
```

不能自动推出“我方 bug”。也可能是第三方库版本差异、默认策略差异、支持范围差异或真实的算法分歧。

5. 工程接入不是做不到，但不是纯 TS 零成本：

- `sxtwl_cpp` 使用 SWIG，官方提供 Python/Lua/Java 等绑定；
- PyPI 有 `sxtwl`，但 2.0.7 的预编译 wheel 主要覆盖较旧 CPython 版本，CI 最稳妥的做法是固定 Python 3.9 runner，或自行验证源码编译；
- 未找到官方维护的 JS/WASM 绑定，WASM 路线标为未验证。

见 [sxtwl PyPI 发布文件](https://pypi.org/project/sxtwl/)。

- 推翻文档：

推翻 §11.2：

> “天文层同时跑三个独立开源实现并进 CI”

其中“独立”不成立。

推翻判定表：

> “一致 / 不同 / — → L1，问真错，可摆证据”

以及：

> “不一致 / — / — → 我方 bug，CI 拦下”

也推翻标题里的强主张：

> “三源对账（把‘我们准’变成证据链）”

- 建议怎么改：

把机制降级为“差分回归”，不要叫三个独立裁判。至少分两级：

```text
第一级：先标准化时间、时区、夏令时、真太阳时、sect、交节基准
第二级：分别比较天文原语
  - 节气绝对时刻
  - 公历/儒略日
  - 连续纪日
  - 年/月/日/时柱
```

判定表应改成：

```text
三源一致、与问真不同 → 有力差异证据，仍需排除输入与 L3 配置后才能归 L1
三源不一致 → 差分失败；定位到具体原语或策略，不预判是谁的 bug
```

若需要真正的 L1 证据，应指定一个可追溯的权威历表或天文算法作为基准，而不是按“三票多数”判真。

## 重大项

### M-1：夏令时结束重复小时缺少可表达的输入

- 攻击面：3
- 判定：重大
- 证据：

结束日法定钟表从 02:00 回拨至 01:00，会出现两次本地 `01:00–01:59`：

```text
第一次 01:30：仍处夏令时，回拨后为标准时 00:30
第二次 01:30：已是标准时，仍为标准时 01:30
```

相同输入字符串“结束日 01:30”因此可以对应两个不同瞬间，标准时间分别是 00:30 和 01:30，时支分别可能为子、丑。

普通字段：

```text
出生日期 + 出生钟表时 + 出生地
```

不足以区分这两个瞬间。必须增加类似：

```text
timeFold = first | second | unknown
dstOffset = +01:00 | +00:00
```

或在无法获知时输出两个候选盘。

日柱方面，两次通常仍在同一公历日期；但叠加真太阳时和子时换日策略后，西部地区仍可能出现日期/日柱候选差异，不能只处理时柱。

- 推翻文档：

推翻 §12.1：

> “结束日 01:00–02:00 重复一小时……回归集要有一条”

一条回归用例只验证已知 fold 的算法，不能解决现实输入本身的二义性。

也削弱 §7.2：

> “B 档先精确到分钟”

精确到分钟仍不足以唯一表示重复小时。

- 建议怎么改：

明确数据模型、录入 UI、审计 JSON 和未知 fold 的双结果行为。否则所谓“唯一正确的 L1”在这批输入上无法成立。

### M-3：交节扫描依赖历法能力

- 攻击面：7
- 判定：重大
- 证据：

前三项所需能力分别为：

| 判据 | 是否需要排盘引擎 |
|---|---|
| 是否在夏令时窗口 | 不需要；需要经核定的政策时间表和带时区时间处理 |
| 真太阳时翻转区 | 不需要四柱引擎；但需要 EoT 算法或表 |
| 23:00–01:00 子时 | 不需要；普通时间区间判断即可 |
| 距交节 < 6 小时 | **需要节气绝对时刻的算法、预计算表、API 或历法库** |

“交节”不是固定公历日期或固定钟点。要判断出生瞬间与立春、惊蛰等“节”的距离，必须先求该年对应节气的绝对时刻。`sxtwl` 等库正是通过节气儒略日提供这项能力。

因此可以“不接完整排盘引擎”，但不能“不依赖任何历法计算能力”。

- 推翻文档：

推翻 §13 标题：

> “先行动作（不依赖引擎）”

并限制 §13.1：

> “只需要出生日期时间 + 出生地经度，不需要排盘引擎”

如果“引擎”严格只指四柱排盘库，这句话可勉强成立；但必须补充“需要独立节气时刻模块或预计算表”。在当前仓库没有该模块的状态下，“约半天”也偏低。

- 建议怎么改：

改成：

> “前三项不依赖四柱引擎；交节风险需要节气时刻库或经验证的预计算表。扫描器只产风险标记，不生成四柱。”

## 次要项

### N-1：903 是时长，不是 909 个完整自然日

- 攻击面：1
- 判定：次要
- 证据：

按文档给出的、尚待国务院公告核实的 02:00 切换时刻独立计算：

| 年 | 起止 | 时刻差天数 | 首尾日期均计入的日期数 |
|---|---|---:|---:|
| 1986 | 05-04 02:00 → 09-14 02:00 | 133 | 134 |
| 1987 | 04-12 02:00 → 09-13 02:00 | 154 | 155 |
| 1988 | 04-10 02:00 → 09-11 02:00 | 154 | 155 |
| 1989 | 04-16 02:00 → 09-17 02:00 | 154 | 155 |
| 1990 | 04-15 02:00 → 09-16 02:00 | 154 | 155 |
| 1991 | 04-14 02:00 → 09-15 02:00 | 154 | 155 |
| 合计 |  | **903** | **909** |

六年总长度：

```text
1986-01-01 → 1992-01-01 = 2191 天
903 / 2191 = 41.2141%
```

所以 `903/2191=41.2%` 数学正确，但措辞“夏令时天数”不够严密；它是六段精确生效时长合计。每个起止日只有部分时段处于夏令时。

- 推翻文档：

不推翻比例结论，只要求修改 §12.1：

> “夏令时占这 6 年 41.2% 的天数（903 / 2191）”

- 建议怎么改：

写为“按表中 02:00 切换时刻，六段夏令时累计生效 903×24 小时，占六年总时长 41.214%”。

### N-2：EoT 区间下界属于近似算法，不宜写成真实全年范围

- 攻击面：4
- 判定：次要
- 证据：

我用 NOAA/Meeus 高阶方程，以 1986–1991 每日北京时间 12:00 共 2191 个采样点复算，得到：

```text
EoT 最小值 = −14.3052 分钟
EoT 最大值 = +16.4621 分钟
```

文档值：

```text
−14.6 ～ +16.5 分钟
```

差异：

```text
下界差约 +0.295 分钟
上界差约 −0.038 分钟
```

简单常见近似式：

```text
B = 360° / 365 × (N − 81)
E = 9.87 sin(2B) − 7.53 cos(B) − 1.5 sin(B)
```

能得到约 `−14.60～+16.45`，说明文档区间对应简化公式。NOAA 说明其太阳计算基于 Meeus《Astronomical Algorithms》；该量级误差远小于时辰跨度。[NOAA 计算说明](https://gml.noaa.gov/grad/solcalc/calcdetails.html)

- 推翻文档：

不推翻 §12.2 量级结论，只要求收窄：

> “均时差按 Meeus 近似，全年 −14.6 ~ +16.5 分钟”

- 建议怎么改：

注明“简化近似范围”；正式引擎固定算法版本、采样时刻和符号定义。

### V-3：0–24 小时直接分桶没有污染 §12 数字

- 攻击面：3
- 判定：无效
- 证据：

时辰边界集合是模 24 小时的循环集合：

```text
B = {23, 1, 3, 5, ..., 21}
```

对任意固定偏移 \(d\)，均匀分布下跨越至少一个边界的测度为：

```text
min(|d|, 120) × 12 分钟
```

除以全天 `1440` 分钟，即：

```text
min(|d|, 120) / 120
```

23:00–01:00 必须作为跨午夜的循环桶处理。文档表格数值与该循环公式完全一致，特别是乌鲁木齐使用了 100% 封顶，因此没有表现出把子时错误拆成两个普通桶的数值迹象。

- 推翻文档：不推翻 §12.2。

### V-4：非均匀分布下，§12.2 的点值没有稳健窄区间

- 攻击面：2
- 判定：无效于原点值、但构成不确定性说明
- 证据：

一般形式是：

```text
R_city = Σ日期权重 × ∫ I[时刻 t 经偏移后跨时辰边界] · f_date(t) dt
```

文档没有给 \(f_{date}(t)\)，所以模型无从识别。

允许出生日期和时刻联合非均匀时，除乌鲁木齐外各城严格区间均为：

```text
0%–100%
```

因为可以把出生全部放在安全区，也可以全部放在当日翻转区。这是数学可行区间，不是现实置信区间。

若固定每天权重相同，但仍允许每天有不同日内分布：

- 其余 11 城仍为 `0%–100%`；
- 乌鲁木齐有 1788/2191 天的绝对偏移至少 120 分钟，这些天任何时刻都会变柱，因此区间为：

```text
1788 / 2191 = 81.61%
到
100%
```

没有历史小时分布，就无法给出可信的、更窄的经验区间。因此 §12.2 的表只能叫“全天均匀基准风险率”，不能称真实客户发生率。

- 推翻文档：不推翻表内数学，只推翻将其外推为“老师天天撞”的频率表达。
